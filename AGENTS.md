# AGENTS.md — правила работы с Dota Pulse

Этот файл действует для всего репозитория. Более близкий `AGENTS.md` в подкаталоге может уточнять правила только для своего дерева. Прямое указание пользователя всегда важнее этого файла.

## 1. Назначение проекта

Dota Pulse — локальное одностраничное приложение для прозрачной аналитики Dota 2:

- анализ форы по убийствам;
- анализ ручного драфта и силы составов по времени;
- разбор матча по Match ID;
- оценка вероятности и статистического запаса без обещаний результата;
- журнал ставок, банк, ROI и статистика;
- локальное хранение и экспорт пользовательских данных.

Приложение не является букмекером и не должно подталкивать пользователя срочно сделать ставку. Любой вывод обязан показывать исходные данные, объём выборки, формулу и ограничения.

## 2. Текущий технологический стек

- React 18;
- TypeScript со `strict: true`;
- Vite;
- React Router;
- Zustand;
- Recharts;
- Zod;
- Dexie / IndexedDB;
- Vitest.

Не заменять стек и не обновлять основные зависимости без необходимости, отдельного обоснования и проверки совместимости. При изменении зависимостей обновлять `package-lock.json`.

## 3. Текущее состояние проекта

Уже реализовано:

- маршруты `/`, `/analysis`, `/analysis/result`, `/bets`, `/settings`;
- адаптивный тёмный интерфейс и основные экраны прототипа;
- валидация формы анализа;
- интерактивный знак форы;
- Zustand-store последнего анализа;
- чистые доменные функции форы, вероятности, прибыли, ROI и просадки;
- unit-тесты доменных формул;
- базовый типизированный OpenDota-клиент;
- Zod-схемы основных ответов OpenDota;
- обработка timeout, 404, 429, 5xx, retry и некорректной схемы;
- безопасный демонстрационный fallback экрана результата.

Ещё не является готовой production-функциональностью:

- реальные ответы OpenDota пока не связаны с пользовательскими экранами;
- CORS прямых браузерных запросов нужно подтвердить реальным smoke-тестом;
- расчёт форы пока использует демонстрационные выборки матчей;
- режимы ручного драфта и Match ID честно заблокированы до подключения данных;
- схема Dexie неполная, TTL-кэш и миграции не реализованы;
- ставки пока не перенесены полностью в IndexedDB;
- импорт/экспорт, очистка кэша и полное удаление данных остаются заглушками;
- отсутствуют полноценные React Testing Library и project-local Playwright E2E-тесты;
- `src/App.tsx` остаётся крупным файлом и должен декомпозироваться постепенно, без массовой переписи.

Не выдавать перечисленные заглушки за работающий функционал. Если данных нет, показывать честный статус вместо выдуманного результата.

## 4. Роли агентов

### Координатор и ревьюер

Главный агент отвечает за весь цикл, а не только за создание исполнителей:

- изучает запрос и текущее состояние репозитория;
- формирует план и критерии приёмки;
- делит работу на независимые области;
- назначает конкретные задачи с границами файлов;
- следит, чтобы параллельные агенты не редактировали одни файлы;
- дожидается отчётов всех исполнителей;
- самостоятельно просматривает изменения и результаты проверок;
- передаёт объединённое состояние QA-агенту;
- возвращает дефекты профильному исполнителю;
- требует повторный QA после исправления;
- только после финального PASS сообщает пользователю о завершении.

Координатор не должен заканчивать работу после первичного аудита, если остаются разрешённые задачи реализации. Отдельный агент-координатор обычно не нужен: он занимает слот, не добавляя исполнительной мощности.

### Frontend-агент

Зона ответственности:

- React-компоненты и страницы;
- маршрутизация;
- формы, доступность и клиентская валидация;
- Zustand-состояние интерфейса;
- Recharts и визуализация;
- адаптивность и визуальная проверка;
- frontend unit/integration-тесты.

Frontend-агент не меняет формулы, API-контракты и структуру IndexedDB без согласования с координатором или API-агентом.

### API/data-агент

Зона ответственности:

- OpenDota-клиент и endpoint-методы;
- Zod-схемы и нормализация данных;
- доменные типы и чистые расчётные функции;
- Dexie, миграции, TTL-кэш и stale fallback;
- API-key, лимиты, retry и обработка ошибок;
- unit и contract-тесты data-слоя.

API-агент не меняет визуальный дизайн и пользовательские тексты без согласования с координатором или frontend-агентом.

### QA-агент

Зона ответственности:

- независимая проверка объединённого результата;
- проверка формул на подготовленных примерах;
- unit, integration и E2E-сценарии;
- browser console, responsive и persistence-проверки;
- фиксация дефектов с приоритетом и воспроизводимыми шагами;
- повторный тест после исправлений.

QA-агент не исправляет продукт сам, если координатор явно не назначил ему реализацию. Статус `PASS` разрешён только после фактических проверок.

## 5. Обязательный многоагентный цикл

Если пользователь явно попросил использовать агентов и задача допускает разделение:

1. Координатор выполняет короткий аудит и составляет критерии приёмки.
2. Каждому исполнителю выдаётся конкретная ограниченная задача, а не только просьба «посмотреть проект».
3. Параллельно выполняются только задачи с непересекающимися файлами или чётко согласованными интерфейсами.
4. Каждый исполнитель сообщает:
   - что сделано;
   - какие файлы изменены;
   - какие команды запущены;
   - результаты проверок;
   - известные ограничения и риски.
5. Координатор читает отчёты и изменения, а не принимает заявление исполнителя на веру.
6. Объединённое состояние передаётся QA.
7. Каждый дефект возвращается ответственному исполнителю с точным ожидаемым результатом.
8. После исправления QA выполняет целевой ретест и базовую регрессию.
9. Координатор завершает работу только после PASS или честно описанного внешнего блокера.

Если главный агент отправил финальный ответ пользователю, активный координационный цикл закончился. Поэтому при поручении «продолжай до результата» не отправлять финальный ответ между этапами; использовать промежуточные обновления и продолжать назначать задачи.

## 6. Совместная работа в одном worktree

Все агенты видят одни и те же файлы. Поэтому:

- перед изменениями объявлять координатору предполагаемые файлы;
- не перезаписывать изменения другого агента;
- не форматировать весь файл ради небольшой задачи;
- не использовать `git reset --hard`, `git checkout --`, массовое удаление или другие разрушительные команды;
- не восстанавливать файл из Git, если в нём могут быть пользовательские изменения;
- при неожиданном изменении остановиться и согласовать владельца файла;
- после параллельной работы обязательно запускать проверки на объединённом состоянии.

В текущем окружении Git может сообщать `dubious ownership`. Для read-only команд использовать локальный параметр:

```powershell
& 'C:\Program Files\Git\cmd\git.exe' -c safe.directory=D:/myproject/Dota status --short
```

Не изменять глобальный Git config без разрешения пользователя.

## 7. Структура и владение кодом

- `src/App.tsx` — текущая композиция страниц; новые крупные функции постепенно выносить из него.
- `src/styles.css` — общие стили и responsive-правила.
- `src/stores/` — небольшие Zustand-store текущего экрана и UI-состояния.
- `src/domain/` — чистая детерминированная бизнес-логика без React, fetch, Dexie и DOM.
- `src/api/` — HTTP-клиент, Zod-схемы, DTO и нормализация OpenDota.
- `src/db.ts` и будущие `src/db/` — Dexie-схема, миграции и репозитории.
- `scripts/` — локальные проверки и автоматизация разработки.
- `artifacts/` — результаты визуальной QA; не использовать как источник данных приложения.
- `dist/`, `node_modules/`, `*.log`, `*.tsbuildinfo` — генерируемые файлы; вручную не редактировать.

Предпочтительное направление декомпозиции:

```text
src/
  app/
  pages/
  widgets/
  features/
  entities/
  shared/
  api/
  db/
  domain/
  stores/
```

Не проводить одномоментную миграцию всей структуры. Выносить модули по мере реализации конкретной функции и сохранять работающую сборку после каждого шага.

## 8. TypeScript и React

- Сохранять `strict: true`.
- Не добавлять `any`, необоснованные type assertions и `@ts-ignore`.
- Данные внешнего API сначала имеют тип `unknown`, затем проверяются Zod.
- Доменные функции должны быть чистыми и тестируемыми.
- Не хранить большие массивы матчей в Zustand; они принадлежат IndexedDB/repository-слою.
- Zustand хранит только состояние, нужное текущему экрану.
- Не дублировать вычисляемое состояние, если его можно безопасно получить из источника.
- После изменения team/hero selection проверять, что зависимый выбор не стал устаревшим.
- Асинхронные действия обязаны иметь loading, success, empty и error состояния.
- Кнопка повторного запуска блокируется во время активного запроса.
- Не оставлять таймер или mock-переход, который выглядит как реальный анализ.

## 9. OpenDota и сетевой слой

- Базовый URL: `https://api.opendota.com/api`.
- API-key необязателен, не вшивается в код и хранится только локально.
- Пользователь должен видеть предупреждение, что frontend-ключ доступен владельцу браузера.
- Не логировать API-key и не включать его в экспорт по умолчанию.
- Все ответы проверяются Zod; повреждённые данные не записываются в БД.
- Использовать `AbortController` и конечный timeout.
- Retry разрешён только для 429 и временных 5xx, с ограниченным числом попыток.
- Учитывать `Retry-After`, но ограничивать максимальную задержку.
- Не использовать случайный публичный CORS-proxy.
- До глубокой интеграции выполнить браузерный CORS smoke-тест для:
  - `/heroStats`;
  - `/teams`;
  - `/teams/{team_id}/matches`;
  - `/matches/{match_id}`.
- Если прямой CORS не работает, остановить интеграцию и сообщить, что требование «без backend» требует пересмотра.
- Ограничивать параллелизм запросов матчей до 2–3, дедуплицировать in-flight запросы и использовать cache-first.

## 10. IndexedDB и кэш

Целевые таблицы:

```text
bets
analyses
cachedMatches
cachedTeamMatches
cachedTeams
cachedHeroes
cachedHeroMatchups
cachedHeroDurations
```

Запись кэша должна содержать как минимум ключ, payload, `savedAt` и `expiresAt`. Плановые TTL:

- список героев — 7 дней;
- статистика героев — 24 часа;
- список команд — 24 часа;
- последние матчи команды — 1 час;
- завершённый матч по ID — бессрочно;
- выполненный анализ — бессрочно.

Для устаревшего кэша допускается fallback с явной подписью возраста данных. Кнопка «Обновить» должна обходить свежий кэш. Каждое изменение версии Dexie сопровождается миграцией и тестом сохранности существующих данных.

В `localStorage` допустимы только небольшие настройки и черновик формы. Большие массивы и ставки хранятся в IndexedDB.

## 11. Неизменяемые формулы и правила

### Фора по убийствам

Для выбранной команды:

```text
margin = selectedKills + signedHandicap - opponentKills
```

- `margin > 0` — выигрыш;
- `margin < 0` — проигрыш;
- `margin = 0` при целой линии — возврат;
- убийства являются неотрицательными целыми числами.

Сглаживание:

```text
frequency = (wins + 1) / (matches + 2)
```

Вероятность без H2H:

```text
P = 0.5 * teamFrequency + 0.5 * opponentFrequency
```

При наличии минимум трёх очных карт:

```text
P = 0.4 * teamFrequency + 0.4 * opponentFrequency + 0.2 * h2hFrequency
```

```text
breakeven = 1 / odds
edge = P - breakeven
```

Статусы:

- меньше 10 карт хотя бы в одной основной выборке — `insufficient_data`;
- edge меньше 3 п.п. — `no_edge`;
- edge от 3 до 8 п.п. включительно — `borderline`;
- edge больше 8 п.п. — `statistical_edge`.

Регрессионный пример:

```text
17/20 -> 18/22 = 81.818%
14/20 -> 15/22 = 68.182%
2/3   -> 3/5   = 60.000%
P = 40% * 81.818% + 40% * 68.182% + 20% * 60.000% = 72.000%
При odds 1.65: breakeven = 60.606%, edge = 11.394 п.п.
```

Не изменять формулы ради более привлекательного результата.

### Банк и ставки

Обычная ставка:

- win: `stake * (odds - 1)`;
- loss: `-stake`;
- refund: `0`.

Фрибет без возврата номинала:

- win: `stake * (odds - 1)`;
- loss/refund: `0` денежных рублей.

```text
ROI = profit / turnover * 100%
```

Нулевой оборот даёт ROI 0, а не `NaN` или бесконечность. Фрибеты и реальные деньги считаются отдельно.

## 12. Валидация и ошибки

Обязательные проверки:

- odds строго больше 1;
- ставка неотрицательна;
- команды непустые и разные;
- выбранная команда принадлежит текущей паре;
- Match ID непустой и содержит только цифры;
- в драфте ровно 10 уникальных героев;
- один герой не может находиться в обеих командах;
- импортируемый JSON проверяется Zod до записи;
- нельзя сохранять рассчитанную ставку без выбранного исхода.

Пользователь должен получать понятное сообщение, а не пустой экран. Поддерживать состояния:

- команда/матч не найдены;
- найдено несколько похожих команд;
- матч не обработан или не содержит пиков;
- недостаточно матчей;
- сеть недоступна;
- превышен лимит;
- используется кэш;
- данные OpenDota имеют неожиданную схему.

Ошибки формы должны быть связаны с полями и доступны screen reader (`aria-invalid`, `aria-describedby` или `role="alert"` по ситуации).

## 13. Дизайн и UX

- язык по умолчанию — русский;
- тема по умолчанию — тёмная;
- desktop-first, полноценная ширина от 1024 px;
- мобильный режим не должен обрезать действия и критические значения;
- команда A — голубая, команда B — оранжевая;
- зелёный используется только для положительного результата;
- красный — для отрицательного;
- жёлтый — для пограничного результата или предупреждения;
- статус не должен зависеть только от цвета;
- интерфейс не копирует букмекерскую контору и не создаёт срочность;
- любые вероятности сопровождаются дисклеймером и исходными данными.

После заметных UI-изменений обязательна визуальная проверка desktop и mobile. Проверять также горизонтальный overflow, таблицы, контраст, focus state и browser console.

## 14. Тесты и команды проверки

Основные команды:

```powershell
npm test
npm run typecheck
npm run build
```

Если `node`/`npm` отсутствуют в PATH текущего Windows-окружения:

```powershell
& 'C:\Program Files\nodejs\npm.cmd' test
& 'C:\Program Files\nodejs\npm.cmd' run typecheck
& 'C:\Program Files\nodejs\npm.cmd' run build
```

Минимальная проверка зависит от изменения:

- документация — проверить ссылки, пути и команды;
- domain/API — unit-тесты, typecheck, build;
- React/store — unit/integration-тесты, typecheck, build;
- UI — предыдущие проверки плюс desktop/mobile browser smoke;
- IndexedDB — migration/persistence test и перезагрузка страницы;
- полный пользовательский поток — project-local Playwright E2E.

Не считать наличие внешнего или bundled Playwright заменой project-local зависимости для committed E2E. До добавления Playwright допускается ручной browser smoke, но это ограничение указывается в отчёте.

Если тест не запускался, писать `не запускался`, а не `PASS`.

## 15. Definition of Done

Задача готова, только когда:

- выполнен пользовательский сценарий, а не только нарисован интерфейс;
- демонстрационные данные не маскируются под реальные;
- входные данные связаны с результатом;
- ошибки и пустые состояния обработаны;
- TypeScript не содержит ошибок;
- релевантные unit/integration/E2E-тесты проходят;
- production build проходит;
- browser console не содержит новых ошибок;
- данные сохраняются после перезагрузки, если это часть сценария;
- UI проверен на нужных ширинах;
- QA подтвердил исправления;
- координатор перечислил изменённые файлы, проверки и оставшиеся ограничения.

Предупреждение Vite о размере chunk не является ошибкой сборки, но его нельзя игнорировать бесконечно: при дальнейшем росте приложения использовать route-level lazy loading и разумное разделение vendor-кода.

## 16. Безопасность и целостность данных

- Не хранить секреты в репозитории.
- Не печатать API-key в console, error telemetry или экспорт.
- Не выполнять внешние действия от имени пользователя без явного запроса.
- Не удалять пользовательские данные без подтверждения.
- Перед полным удалением показывать точный объём и последствия.
- Импорт должен быть атомарным: повреждённые данные не записываются частично.
- Денежные вычисления должны иметь определённое правило округления на границе представления, а внутренние формулы не округляются преждевременно.

## 17. Кодировка и работа с файлами

- Все исходники и документация — UTF-8.
- Не выполнять массовую перекодировку без доказанной проблемы.
- В Windows PowerShell 5 вывод UTF-8 без BOM может выглядеть как mojibake, хотя файл корректен. Перед исправлением проверить файл Node.js или редактором с явным UTF-8.
- Для локальных правок использовать точечный patch и сохранять пользовательские изменения.
- Генерируемые файлы не редактировать вручную.

## 18. Формат итогового отчёта агента

Каждый исполнитель завершает поручение кратким отчётом:

```text
Результат: PASS / FAIL / BLOCKED
Сделано:
- ...

Изменённые файлы:
- ...

Проверки:
- команда — результат
```

## 20. React / Airbnb-compatible conventions

- Для задач по React-архитектуре использовать skill `react-best-practices`, если он доступен в текущей сессии, и сверяться с официальными Airbnb JavaScript/React Style Guides. Если skill недоступен, этот файл и checked-in ESLint-конфигурация остаются обязательным минимумом.
- `src/App.tsx` содержит только композицию маршрутов, `React.lazy` и `Suspense`; экраны находятся в `src/pages/`, а каркас приложения — в `src/app/`.
- Один именованный React-компонент располагается в отдельном файле. Имена компонентов — `PascalCase`, props — отдельный TypeScript interface, hooks — `use*`, остальные значения — `camelCase`.
- Не использовать barrel-файлы (`index.ts`) для внутренних модулей: импортировать непосредственно из файла. Это соответствует правилу `bundle-barrel-imports` и сохраняет предсказуемые чанки Vite.
- Тяжёлые страницы и графики должны загружаться на уровне маршрута через `React.lazy`. Не помещать Recharts в статический entrypoint.
- Не определять компоненты внутри компонентов. Производные значения вычислять во время рендера, а обновления, зависящие от предыдущего состояния, выполнять функциональным `setState`.
- ESLint 9 flat-config не подключает устаревший `eslint-config-airbnb`: его legacy-конфигурация несовместима с flat-config и TypeScript ESLint. Эквивалентные актуальные правила обеспечивают `eslint`, `typescript-eslint`, `eslint-plugin-react`, `react-hooks` и `jsx-a11y`; дополнительно включено требование function declarations для named components. Команда: `npm run lint`.

## 21. SCSS / BEM

- Исходные стили пишутся только в `.scss`. Использовать `src/styles/_tokens.scss`, `src/styles/_mixins.scss`, `src/styles/globals.scss` и SCSS рядом с компонентом или страницей.
- Собственные классы используют BEM: `.block`, `.block__element`, `.block--modifier`; nesting — не глубже трёх уровней, без `!important` и ID-селекторов.
- `npm run lint:styles` запускает Stylelint для SCSS, включая `selector-class-pattern` с BEM-паттерном. Глобальные reset/third-party selectors допускаются только в изолированном файле с комментарием о причине.
- Для собственных стилей исключений Stylelint нет: каждый SCSS-файл обязан проходить BEM-проверку. Глобальные reset и vendor-стили должны быть минимальны, изолированы и сопровождены комментарием о причине.
